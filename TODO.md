- [x] TODO[LB-01](lootable-bodies:enchantments): Add Soulbound enchantment. Done 2026-09-06 — `whatremains:soulbound`, 3 levels, `EnchantmentCategory.BREAKABLE` (any damageable weapon/tool/armor piece, matching the TODO's "any enchantable-compatible item" scope), RARE rarity, not treasure/curse, obtainable at the enchanting table and via anvil books. `SoulboundEnchantment` (identity only) + `SoulboundHandler` (roll/stash/restore) + `WREnchantments` registry. At death, `PlayerDeathHandler` rolls a per-item, per-slot chance (`WhatRemainsConfig.soulboundChancePerLevel`, default 35/60/85% for levels 1-3, admin-tunable, master-switched by `enableSoulbound`) instead of sending an enchanted armor/offhand/main-inventory stack to the corpse. A kept item is serialized into the dying player's `getPersistentData()` (Forge's own survives-death/logout NBT bag) and handed back on `PlayerEvent.Clone` (`isWasDeath()` only) — required because a fresh respawn inventory is otherwise empty regardless of what the dead entity's arrays still held; occupied-slot/leftover-space restores fall back to `ItemHandlerHelper.giveItemToPlayer`. Exploit/duplication pass (per the TODO's own ask): every item either copies-to-corpse-and-clears or stashes-and-clears, never both; main-inventory kept stacks get the exact same `CorpseEntity#applyItemDamage` durability hit vacuumed items already take (so Soulbound can't be used to dodge `itemDamageOnDeath`) while armor/offhand kept items correctly take none (parity with their existing no-damage corpse path, not a new exemption); a forged/out-of-range NBT level clamps to the highest configured chance instead of exceeding it; a stash left over from an aborted death is cleared before the next death's rolls begin. `compileJava --offline` BUILD SUCCESSFUL. IN-GAME TESTING PENDING. **Follow-up (2026-09-06, same day, uncommitted):** re-homed vanilla's Curse of Binding and Curse of Vanishing onto this same system, since this mod's corpse-vacuum loops never run vanilla's own drop/curse code at all — without this neither curse had ANY effect here. `SoulboundHandler` renamed to `ItemRetentionHandler` (it's no longer Soulbound-specific) and gained `isBound`/`isVanishing`; `PlayerDeathHandler`'s three transfer loops now dispatch through one `resolveDeathOutcome` (Vanishing → destroy, checked first and taking precedence over everything else on the same stack; Binding → unconditional keep, same slot, through respawn; else a Soulbound roll; else the corpse), each independently config-gated (`enableCurseOfBindingKeep`, `enableCurseOfVanishingDestroy`, both default true). Binding reuses the identical persistent-data stash/`PlayerEvent.Clone` restore path Soulbound already needed. `compileJava --offline` BUILD SUCCESSFUL. IN-GAME TESTING PENDING. **Redesign (2026-09-06, same day, uncommitted, supersedes the Binding paragraph above):** user reconsidered Binding's death-time "stays with player" behavior in favor of a corpse-side lock — a bound armor piece now transfers into the corpse completely normally (no longer a `PlayerDeathHandler`/`ItemRetentionHandler` concern at all; `isBound`/`enableCurseOfBindingKeep` removed) and instead can never be removed from its corpse armor slot — not via the GUI (`CorpseMenu`'s armor `Slot#mayPickup`, plus a `quickMoveStack` guard closing the shift-click bypass that path never checked before) and not via a hopper (`CorpseEntity` is a plain `Container` a hopper can pull from directly, bypassing the Menu entirely — closed in `removeItem`/`removeItemNoUpdate`) — until the corpse itself is destroyed (buried/decayed/collapsed), at which point `dropAllItems()` frees it like everything else, since that method writes straight to the backing list rather than calling either guarded method. Gated by new `enableCurseOfBindingLocksToCorpse` (default true). Confirmed as a side-finding: armor/offhand slots were ALREADY exempt from the general-inventory decay slot-lock eviction (`isSlotActive` returns true unconditionally for indices < `GENERAL_START`) — no code change was needed for that part. **Also same day:** SKELETAL's duration decoupled from the shared `decayLifespanDays` fraction table — it now reads its own `skeletalStageLifespanDays` (default 20.0 days, ~8x the whole FRESH..ADVANCED_DECAY progression) via `DecayStage#getDuration()`'s special case, so a corpse reduced to bones persists far longer before it actually collapses ("bone degrades slower"). `DecayStage#getFullLifespanTicks()` added for the real total including the extended stage (used by the Jade "time until collapse" tooltip, now fixed); the render pipeline's `getTotalLifespanTicks()`/visual-step quantisation was deliberately left untouched, since `CorpseFleshBaker#resolve` and `CorpseHeldItemLayer#computeDecayPoseRow` both already short-circuit before reading SKELETAL's numeric progress at all — verified by reading both guards directly rather than guessing, per this repo's own "measure before fixing" precedent on flesh-render changes. `compileJava --offline` BUILD SUCCESSFUL.
